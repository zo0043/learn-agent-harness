## 3. 内容缺口（确认的真空白，按价值排序）

> **处置状态：✅ 已落地（2026-10-19）**——`notes/agent-harness.md` §3.1 就地划改（"每次模型调用都附带工具定义"补边界条件）、新增 §3.4 工具发现三形态表；`notes/mcp.md` 新增 S2.2「协议给全量，裁剪是 host 的事」。全部数字经 Anthropic 一手源 2026-10-19 逐条复核。

### A1【P0 · 需修正旧表述 + 补新模式】工具发现与 tool-as-code

**现状矛盾**：`notes/agent-harness.md:41` 写「**每次模型调用都附带工具定义**」——这是 2025 中的默认做法。2025-11-24 Anthropic《Introducing advanced tool use》给出反例：58 个工具 ≈ 55K token 预付，>40 工具即显著退化；Tool Search Tool 让 token **-85%**，Opus 4 工具选择准确率 49%→74%。同月《Code execution with MCP》进一步：把 MCP server 呈现为文件树/代码 API，agent 按需读工具文件、在代码里过滤数据，实测 **150K→2K token（-98.7%）**，Cloudflare Code Mode 独立得出一致结论。

本仓 `notes/mcp.md` 只在 **ASI05 Unexpected Code Execution** 把代码执行当**攻击面**讲（:237），完全没有「代码执行也可以是 token 优化手段」这一面——读者会形成「代码执行=危险」的单向认知。

**建议**：
- `agent-harness.md` §3.1 就地划改：「每次调用都附带工具定义」→ 加上边界条件（工具数阈值、按需发现、defer_loading 不进 cache key 不破坏 prompt caching）
- `mcp.md` 新增一节「工具发现的三种形态」：全量预载 / Tool Search Tool / tool-as-code，各自适用条件与 token 账
- 可复现实验（本仓强项）：在 `mcp-demo` 或 `agent-harness` 加一个小实验，量化「N 个工具全量预载 vs 按需发现」的 token 差

**证据**：https://www.anthropic.com/engineering/advanced-tool-use ｜ https://www.anthropic.com/engineering/code-execution-with-mcp

> **处置状态：✅ 已落地（2026-10-19）**——`notes/evaluation.md` S1 补七词词汇表；S2 补 pass^k、capability/regression 分离、eval saturation、评估 hygiene；S3 补三条校准纪律（Unknown 退路 / 分维度隔离 / judge 上限=标注者间一致率）。

### A2【P0】evals 结构化学：词汇体系 + pass^k + saturation + judge 校准纪律

`notes/evaluation.md` 已有 S3 judge 设计校准、S4 轨迹评测、S5 golden set、S6 CI 门禁、S9 校准完整走查——**骨架相当完整**。缺的是 2026-01 Anthropic《Demystifying evals for AI agents》立起的**词汇与判别纪律**：

- 术语体系：task / trial / grader / transcript / outcome / harness / suite（本仓散用「评测/判据/断言」多套词）
- **pass@k vs pass^k**：本仓只有 pass@k（:42-47），缺 pass^k（k 次全对才算过）——两者读法相反，混用会得出错误结论（75% 单 trial × 3 次 = 42%）
- **eval saturation**：SWE-bench Verified 一年 ~30%→>80%，分数欺骗性上升——本仓 `notes/model-basics.md` 与 `rag.md` 有「饱和」字样但未作为评测纪律讲
- **judge 的 Unknown 退路 + 分维度隔离评分**（而非一个 judge 评全部）+ rubric artifacts 缺陷机理（arXiv 2609.02942：judge 靠 rubric 表层特征捷径判断）
- **capability evals vs regression evals** 的分离（低通过率爬山 vs 近 100% 守门）——本仓 S6 讲 CI 门禁但未做这个区分

**证据**：https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents

### A3【P1】跨窗口 harness：initializer / coding agent 模式

`notes/durable-execution.md` 讲透了 checkpoint/journal/幂等/恢复，但 2025-11-26 Anthropic《Effective harnesses for long-running agents》指出** compaction 不足以跨上下文窗口**（即使 Opus 4.5 循环跑也交付不了一个 claude.ai clone），方案是 **initializer agent**（init.sh + claude-progress.txt + feature_list.json 全量失败态特性清单 + 初始 git commit）+ **coding agent**（每次增量、留干净状态、git commit 总结），并列出四大失败模式（过早宣布完成/留烂摊子/未端到端测试就标完成/每次重学怎么跑应用）。

这与本仓 durable-execution 是**互补而非重复**：前者管「一次任务内不丢不重」，后者管「跨会话/跨窗口怎么接力」。

**证据**：https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents

### A4【P1】METR time horizon 作为长时程能力的标准度量

`notes/evaluation.md` 已引用 METR，但没把 **time horizon**（50% 任务完成时长，doubling ~7 个月，TH1.1：P50 doubling 196 天、2024 以来 89 天——**在加速**）作为「为什么长时程工程越来越重要」的度量锚。这条对 `industry-2026` 与 `durable-execution` 的立论都是加强。

**证据**：https://metr.org/blog/2026-01-29-time-horizon-1-1/

### A5【P1】Cognition Managed Devins 产品事件补记

`notes/industry-2026.md:23` 有 Cognition 立场演化的**结论**，缺 2026-03-19 的**产品证据**：Cognition 推出「Devin can now Manage Devins」——协调器 Devin 把任务分给各自跑在独立 VM 的 managed Devins，理由「context accumulates, focus degrades」。这是「隔离论证」从论文落到产品的标志事件，且与 `notes/multi-agent.md` S9 的「上下文隔离买点」直接互证。

**证据**：https://cognition.ai/blog/devin-can-now-manage-devins

### A6【P2】nemesis 表：把攻击/故障注入提升为一等清单

`mcp-demo` 已有「对照组 ❌ 攻击得逞 → 防御组 ✅ 被拦 → 单层消融 → 确定性重放断言」的结构，教学设计对标认为这其实就是 Jepsen 式「注入故障→观察→判定→消融」的教学化，缺的只是把故障清单**显式命名为一张表**（Jepsen 把 nemesis 做成与 client/generator/checker 并列的一等进程）。建议 `notes/mcp.md` 与 `notes/sandbox.md` 各加一张 nemesis 表 mermaid：行=注入的攻击（tool poisoning / rug pull / 结果注入 / 越权外发），列=对照组/防御组/消融后。与现有 62 张图合计后 CI 的 mermaid 断言（运行时扫 dist）天然兼容，无需手抄清单。

**证据**：https://github.com/jepsen-io/jepsen

### A7【P2】成本工程的定量实证补强

`notes/api-engineering.md` 已有 prompt caching，缺两条 2026 定量实证：**Don't Break the Cache**（500+ agent session，API 成本 -41~80%、TTFT -13~31%，且战略性 cache block 控制优于 naive 全量缓存）与 **gist 压缩**（Shopify：~6000 token 系统提示压到 ~1500，TTFT -19%、端到端 -38%）。这两条正好接本仓已有的「缓存破坏」话题。

**证据**：https://arxiv.org/abs/2601.06007 ｜ https://shopify.engineering/sidekicks-continual-learning-loop

## 4. 工程化缺口（比内容缺口更硬，全部已本仓实证）

### B1【P0 · 最大缺口】9/10 个 demo 零 CI 覆盖

实测：`grep -c <demo目录> .github/workflows/verify.yml .github/workflows/deploy.yml` → **harness-demo / sandbox-demo / mcp-demo / durable-execution-demo / framework-demo / memory-redteam / api-demo / flywheel-demo / model-basics-demo / my-agent 全部 0 次**（唯一例外是 rag-demo 的 `check:corpus` 在 verify.yml:105）。

也就是说：**本仓最核心的教学资产（「讲清每层为什么存在 + 可复现实跑」的那个「实跑」）在 CI 里一次都没跑过。** 口径门禁/类集合门禁/mermaid 回归/3 视口几何全绿，只证明「站点没坏」，不证明「demo 还能跑」。任一 demo 悄悄烂掉（依赖升级、Node 版本、fixture 漂移），门禁全绿。

**建议**：
1. 给每个 demo 统一加 `npm run check` 语义 = demo 跑通 + 内置断言通过 + 退出码 0（`rag-demo` 的 `check:corpus`、`memory-redteam` 的 `test`、`my-agent` 的 `assert:m*`、`framework-demo` 的 `compare:assert` 已有断言，收敛到同一名字）
2. 根 `package.json` 加聚合入口（现在只有 `render` / `check:final`）
3. `.github/workflows/verify.yml` 新增 `demo-check` job：对 10 个目录逐个 `npm ci && npm run check`，与现有 site job 并行、独立 concurrency 组

> 注意代价：`npm ci` × 10 会显著拉长 CI；可先用「改动触达的 demo」做路径过滤（`paths:`），再逐步扩到全量。

### B2【P0】出口自测不可执行

`notes/knowledge-map.md` 每域已有「出口判据」文字（如「能脱稿讲清本课三条核心机制，并能指出一个自己实现里踩过的坑」），但它是**文字**，机器判不了。题库已按用户决定删除，不宜恢复；但可以升级为「**可执行复述**」：每篇讲义末尾加 `## 出口自测` 代码块，内含 3-5 条 `node --test` 风格断言，断言对象是**本课机制的玩具实现**（如 sandbox 断言「默认 deny 下危险动作被拒且副作用未发生」）。判据只描述可观察行为，沿用 `final-project/rubric.mjs` 已有的「黑盒判据不规定实现」原则。

### B3【P1】预备知识块缺 5 篇

实测缺「预备知识/门槛」块：`agent-harness.md` / `harness-from-scratch.md` / `llm-timeline.md` / `rag.md` / `system-design.md`（其余 12 篇已有，如 `long-term-memory.md:17-18` 的「技能门槛 + 不需要提前会」两行式就写得很干净）。补齐并统一标题字串后，可加一条 grep 门禁守着（导览型显式白名单豁免）。

### B4【P1】版本钉死表不统一

教学设计对标建议每个 `*-demo/README.md` 补「版本钉死表」（node 版本 / 关键依赖 / 是否需要 key），与现有「全离线：零网络、零 key」声明并列。目前只有 `mcp-demo` 有离线声明，格式各 demo 不一。

### B5【P2】viz/ 图库按域归档

`viz/` 现在只有 3 个脚本（chrome.mjs / mermaid-check.mjs / render.mjs），图全内联在讲义里。doocs/advanced-java 的「一域一图库」组织可借（但**不借它的面试题叙事框架**）。可在 `notes/process/teaching-style-guide.md` 增一条规定：「每张 mermaid 图必须有一句图注回答：这张图讲清了哪一层的为什么」。
