## 〇、一句话结论

**本轮 CI 被打红不是事故，是一次成功的暴露**：它证明门禁在工作，同时暴露出一个结构性问题——仓里所有「✅ 实跑」的宣称值，靠的是「人记得复跑 + 人手抄副本 + 事后跑门禁」，这条链上有 **三个洞**：① 副本比门禁查得多（recall 14 处落点只查 2 处，`notes/long-term-memory.md:219` 正 displaying 错值而全门禁绿）② 门禁自身会腐化（写死的 125 chunks 判据已被历史叙述喂成恒真）③ 发布路径不校验（`deploy.yml` 与 `site/build.sh` 都不查 corpus）。

升级 = 把「宣称—命令—门禁」三角焊死，分五期：**地基（S0 真源外移）→ 止血（P0 四项）→ 收口（派生链全覆盖）→ 铺开（11 demo 全进 CI）→ 内容（A3-A7/B3-B5）**。

## 一、根因：为什么「补正则」这条路走不通

四组独立 converge 到同一个结论，值得作为总装的第一性原理：

| 组 | 原话要点 |
|---|---|
| 架构组 06 §1.4 | 「chunks 的 8 处副本被全扫描，**recall 的 14 处落点里只有 2 处被查**……这是『补正则』这个修法的结构性缺陷——每加一条判据都要人手决定查哪个文件的哪个字段，**永远追不上副本增长**」 |
| 门禁组 07 §5.3 | 「凡『枚举型』守卫（禁词表/旧值形态/副本清单/扫描面），腐化方向都是**『漏』而不是『误报』**——漏了不红，所以只有人工复审能发现」 |
| CI 组 08 §9 | 「缺的不是测试而是**把测试接进 CI 的那根线**」 |
| 内容组 09 §0 | 「只有 B3 会改 demo 实测值……必须放在内容批次的最后」 |

**根因一句话**：宣称值是**派生物**（由一次测量产生），却被当作**手抄常量**分布在 13-15 处 prose/TS 里；于是每加一处拷贝就多一个腐化点，而守卫只能枚举已知拷贝。

**推论（本方案的总设计原则）**：

> 不再问「哪个文件抄了这个数、要不要加条判据」，而是问「**这个数的唯一机器真源在哪、其余落点是否全部由它派生**」。

## 三、五期实施路线（跨组对齐后的唯一顺序）

> 排序原则：**先做地基，因为它让后面的每一步都变简单；止血项与地基解耦，可并行。**

### 第一期 · 地基：S0 真源外移（P0，架构组 06 §6.1）

**做什么**：机器读取方全部从「正则解析 markdown」切到「`JSON.parse(facts/rag.json)`」。

- 新建 `facts/`（仓库根，每主题一 JSON）+ `facts/registry.json`
- `site/src/utils/ragStats.ts` 改成 JSON loader（保留 `parseRagStats` 导出名与 `RagStats` 接口，`index.astro`/`works.astro` 不用改；fail-closed 不变）
- `check-counters.mjs` 的 §13 解析、`check-corpus.ts` 的声明侧改读 facts
- **`corpus.members` 由生成器从 `corpus.ts:16-20` 读出**——让「语料成员变更」第一次变得可见

**为什么排第一**（架构组原话）：零碰 `notes/` → chunk 数不变 → 无不动点迭代 → **一次性消解机器侧全部三类失效**（自指归零、排版欺骗归零、4 份解析器并为 1 份）。

**验收**：`npm run facts` 落盘且 `chunks=134`/`recall={3:0.31,5:0.38,10:0.56}`；两个门禁 exit 0 且判据不减；**fail-closed 负路径**（facts 里 chunks 改 999 → 站点构建炸 + check:corpus exit 1，两者都响才算过）；**抗欺骗负路径**（rag.md:283 改成 `**134 chunks**` → 门禁仍 exit 0，证明机器已不读这句）。

**与其他期的接线**：这是后面所有期的安全网——S1 的回滚点就是「S0 成果保留」。

### 第二期 · 止血：四条当前即真的失实/腐化（P0，可并行）

| # | 动作 | 归属 | 为什么是 P0 |
|---|---|---|---|

| T2 | `check-classes.mjs:78` replay 基线改构成分解（replay 3 + 白名单 2 + 注释通写 k + 动态 m，与 `analysis/plan/03-form-layer.md:96-112` 比对）；**禁止**直接把 10 改成 14 | 门禁组 | 自证路径已坏且无人知道（不在 CI） |

### 第三期 · 收口：派生链全覆盖（P1）

三件事，都建立在第一期地基上：

1. **S1 · §13 生成区**（架构组 06 §6.2）：定界符 `<!-- facts:generated rag@1 begin/end -->` 圈定机器所属区，区域内 **byte 比对**，配 ≤5 轮有界迭代（不收敛则 exit 1 不写盘）。外沿的历史叙述仍是手写且被明确排除在机器读取之外——这正是现行正则最致命的混淆源。
   - 与 S0 的对照是关键设计：S0 后把生成区改成 `**134 chunks**` 应 **exit 0**（机器不读它）；S1 后同样改动应 **exit 1**（byte 比对）。**两步预期相反，正好证明解析权已从正则转交生成器。**
2. **recall 全副本登记 + 双向核对**（门禁组 07 §6.3）：把 B 组全部 14 处落点登记进 `registry.json`，`facts:check` 逐项比对；同时把 `grepNum` 从「副本含真源值」升级为「副本不含非真源值」。
   - **这一项直接治洞1**：修完后 `notes/long-term-memory.md:219` 那类漂移首次可机检（注入 0.99 → exit 1 且报行号）。
3. **门禁去硬编码 + 变异自证制度化**（门禁组 07 §6.1/§3）：剩余 12 处违规自编迁移到双源派生；check-counters 补 `--self-test`（≥4 变异 + 反向空输入变异，exit 1 = 断言器过弱）；旧值枚举改数字族差集；豁免名单加使用率报告与失效红线（把 `check-classes.mjs:242-253` 的白名单失效检测这个**全仓最佳先例**对称化到 6 套名单）。

### 第四期 · 铺开：11 个 demo 全进 CI（P0/P1，CI 组）

**核心事实（先纠正我上游的一个说法）**：「9/10 demo 零覆盖」不精确——准确是**范围内 9 个 demo 中 8 个零覆盖**（rag-demo 是唯一被覆盖的，且只覆盖 `check:corpus` 一个命令）；若含 my-agent/memory-redteam 则 10/11。

**设计：parallel matrix**（CI 组 08 §4.2 有完整 YAML 草图）：
- 11 个 offline leg，`fail-fast: false`，`timeout-minutes: 10`/leg，按 lock hash 手动 cache，`if: always()` 上传 check.log
- 墙钟增量仅 **+60-90s**（verify 139s → 约 200-230s）；串行方案 +12-20min 已否决
- rag-demo 步骤从 `verify.yml:104-108` 迁入 matrix 后删除，避免 site 之外再装一份 rag 依赖
- **live 线独立 schedule workflow**（secret + `continue-on-error: true`）——live 宣称本质是「对接过真实端点」的历史事实，塞进 PR 门禁只会制造长期红灯狼来了

**出口自测统一定义**（CI 组 08 §5.1）：`npm run check` exit 0 ⇔ 本 demo 对外宣称的全部数值/行为成立。必备五件：数值核对 / 行为探针 / 边界用例 / 确定性双跑 / 负路径 mutation。

**重要边界（CI 组的关键判断，必须写进总装）**：`check:corpus` 作为「**宣称值门禁**」的范本够（真跑不手抄 + 全副本扫描 + 旧值句段豁免 + 响亮失败），作为「**demo 出口自测**」不够（不守行为、拒答轨无断言、副本清单硬编码）——**出口自测 = 它 + 行为断言，两层缺一不可**。

## 六、风险与回滚

沿用架构组 06 §7 的 R1-R12，总装只补三条跨组的：

1. **组织性风险 > 技术风险**：`facts/rag.json` 一坏，站点构建 + 两个门禁同时炸——这是**期望行为**（fail-closed）。真正要防的是「坏了有人顺手删掉门禁」。对策：纪律「只增约束不放宽」+ PR review 清单 + workflow 里禁 `continue-on-error`/`|| true`（架构组 06 §7.2 第 5 条）。
2. **S1 的不动点不收敛**：实测声明段有 139 字符余量（追加 434 字才触发分裂），当前模板约 110 字符，现实余量充分；迭代守卫是给将来的保险。**不收敛时必须 exit 1 不写盘并交给人判断**，不得悄悄接受一个数。
3. **md-log / Obsidian 镜像与生成器抢写 rag.md**：`AGENTS.md` 的 `/md-log` 实时镜像进 `notes/*.md`，与生成器写 §13 可能冲突。对策：生成区有定界符 + `registry.json` 记明「生成区 Owner = facts 生成器」+ **需人工确认一次**。残留中风险（镜像工具若做全文重排，定界符被移动 → `facts:check` 失配 → 响亮失败，可接受）。

**回滚点**：每期都有独立回滚点（S0 = revert commit，未碰 notes/未碰语料，零连带风险；S1 = 删定界符，S0 成果保留）。

## 七、明确的「不做清单」（防止范围蔓延）

1. **不改被测对象**：否决「把 §13 数字删掉」与「让 `loadCorpus()` 切掉声明区」两个方向——前者删课，后者是「为了架构好看而改测量」，属放水（架构组 06 §4.1）。
2. **不把 live 线塞进 PR 门禁**：代理 503 已证明 live 宣称随时不可复现，schedule + continue-on-error + secret 是唯一诚实形态。
3. **`final-project/grade.mjs` 不进 CI**：无参必红是正确语义（未提交），没有成品 = 永久红。
4. **不建纯手工抄写表**（B4 方案 A 已否决）：单一文件靠人守必腐，chunk 数漂移两次（85→132→123）就是教训。
5. **不做搬图片**（B5）：本仓没有图片库，`viz/` 仅 3 脚本、notes 零 PNG/SVG 引用；SVG/PNG 管线维持「按需生成、不入库」。
6. **不为迁就架构放宽任何既有判据**：四组报告共 2019 行，无一条建议放宽；所有改造的验收标准统一为「**故意破坏必须被抓**」。

## 八、验收总纲（怎么判断整个升级做完了）

不是「CI 绿了」——本轮已经证明绿门禁下可以有活漂移。判据是**四条负路径全部成立**：

| # | 负路径 | 期望 |
|---|---|---|
| N1 | 改坏 prose 里任一 recall 落点（如 `long-term-memory.md:219` 的 0.38 → 0.99） | `facts:check` exit 1 且报出 `文件:行号` |
| N2 | 改坏 `facts/rag.json` 的 chunks 且不重新 measure | `facts:check` exit 1 + `check:corpus` exit 1，**两层都响** |
| N3 | 改坏任一 demo 的宣称值（如 api assert.ts 一个期望值） | 对应 matrix leg 红、其他 leg 仍绿（fail-fast: false 生效） |
| N4 | 注掉任一门禁的一条判据 / 改弱其断言器 | 该门禁 `--self-test` exit 1（断言器过弱） |

**再加一条正路径**：`npm run facts` 两连跑第二次零 diff（幂等，证明不动点已收敛）。
