### A2【高】knowledge-map.md 内部自相矛盾：口径块写 32，未结事项写「33 个 html」

## 二、网站显示效果分析

### B1【中】/details/ 列表页渲染完整来源 URL，与详情页处理不一致

`site/src/pages/details/index.astro:119` 把 `item.data.source` 全量塞进 chip（如 `https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf`，90+ 字符）。不溢出（`.dc-top .chip` 有 `overflow-wrap:anywhere` 兜底，类集合门禁也守住了这条规则），但卡片里挂一条长 URL 芯片很丑。而 `details/[slug].astro:29-38` 早已改为只显示 host（注释写明「实测 375px 溢出 197px」后才这么改的）——**同一份数据的两个页面，一个修了一个没修**。

**修法**：列表页复用 `new URL(source).host`（详情页同款三行），完整 URL 留 `title` 属性。

### B2【中】「答到机制层」答题叙事残留在首页与 /details/

- `site/src/pages/index.astro:207`「答到机制层时直接用的素材」
- `site/src/pages/details/index.astro:51`「答到机制层时直接可用」

「答到 X」是面试答题语境；按新定位应改「讲到机制层时可直接引用/查用」。

### B3【低】route-grid 五列断点 1000px：1000–1080px 区间每列约 190px

`index.astro:279-294`：`repeat(5, 1fr)` @1000px，而 `.wrap` max-width 1080px——恰好落在断点上的视口（如 1024×768 iPad 横屏）五列各 ~190px，`route-list` 内课程名链接（如「durable execution」）会频繁换行。**留浏览器目检**（本机无构建，不做像素断言）；若目检确认拥挤，把断点提到 1100px 或改 `repeat(auto-fit, minmax(170px, 1fr))`。

### B4【低】mermaid 图形正确性仍无 CI 守卫（工具已存在但未接线）

`site/tools/visual-check.mjs` 只断言「mermaid 渲染出了 svg + data-processed」，**不判图形内容对不对**（宪章 §四 自己也记了这条）。`viz/mermaid-check.mjs` 正是干这个的（起服务、逐页确认渲染成 `<svg>`、统计非 200 资源），但只在本地跑、不在 CI。verify.yml 在「Serve dist」步已经有浏览器和本地服务，**加一步 `node viz/mermaid-check.mjs --dist=site/dist` 即可把「语法错/渲染失败」纳入 CI**——这是当前性价比最高的一条显示层补强。

### B5【低】shiki 暗色方案靠 `!important` 覆盖内联样式

`global.css:557-563` 用 `!important` 压 shiki 内联亮色（注释已实证「不加 !important 无效」）。有效但脆：shiki/astro 升级若改内联方式会**静默失效**（暗色下代码块变白底）。无立即风险；记录在案，升级 shiki 时须重验。

### B6【信息】本机 `site/dist` 仍是「89 文件 / 0 HTML」残骸

本机实测 `find site/dist -name '*.html' | wc -l` = 0。因此本报告中一切渲染面结论均为**源码推演 + 门禁交叉验证**；所有涉及像素/排版的判断（B3、B5 及一切「页面看起来」）**留浏览器目检**，不得拿本机状态推断线上。线上证据以上轮 CI 绿 + 公开 URL 为准。

### B7【低·亮点】显示层已相当成熟，不建议大改

通读 `global.css`（1741 行）与全部组件后的总体判断：明暗双主题 + AA 对比度（注释带 node 实算值）/ skip-link / :focus-visible / 汉堡浮层焦点陷阱 / 阅读进度条 / 上下篇 / works sticky 标签栏 / measure 40em 收口 / prefers-reduced-motion / 表格宽表横滚——这些都是**已闭环的设计**，且都有 CI 断言或负路径自证守着。本轮显示层的问题全是「点状残留」（B1/B2/B3），不是结构性问题。**建议不要重写样式，只做点状修**。

## 三、内容渐进性（pedagogy / progressive disclosure）分析

### C1【中】details ↔ 课程**双向断链**：分水岭是「死胡同」页

设计上 `notes/details/` 8 篇是课程的分水岭深化（每篇有「已覆盖/未覆盖」本地映射，指向具体课程节），但：

- details 页引用课程全是**纯文本**（如 01-context-rot.md:26「Harness 架构 §5.1 … 从零写 harness §8」）——渲染后不可点；
- 17 门课程笔记**无一**以链接形式指向 details 页（`grep -rn "details/" notes/*.md` 仅命中 knowledge-map 的资产清单）；
- details 页 footer 只有「详解列表/学习路线」两个通用链接。

⇒ 读者在 /c/agent-harness/ 读不到「本篇 §5 对应的分水岭在 /details/01-context-rot/」；在 /details/01-context-rot/ 也无法点回「Harness 架构 §5.1」精确锚点。**渐进披露的最远一跳断了**。

**修法（低成本）**：① details 每篇「本地映射」的课程引用改为站内链接（`/c/agent-harness/#51-…` 锚点由 `extractToc` 的 slug 算法可算）；② 在对应课程笔记的对应节末尾加一行「延伸分水岭：[context rot](../details/01-context-rot.md)」——课程页 markdown 管线原生支持相对链接，渲染层零改动。

### C2【中】线性序 #1 是横向资产，「从第一课开始」按钮与 #1 不一致

`course-structure.ts` 数组序：#1 = `llm-timeline`（`isHorizontal: true`，#17 又是 `industry-2026`，同样横向）。后果：

- `/learn/` 的「建议开课顺序」链以 LLM 时间线开头，上下篇导航把 `llm-timeline ↔ harness-from-scratch` 连成相邻课；
- 首页「从第一课开始」按钮指向 `c/harness-from-scratch/`（不是 #1）——两个「第一课」信号矛盾；
- 横向课排在线性序里，会让「17 门课线性主线」混入 2 门非主线（nav.astro 的 compact 索引用「横向」chip 区分了，learn 的顺序链没有）。

title 字段已写「序章横向/横向收口」，但顺序链本身无线索。**修法（二选一）**：① 把两门横向课移出线性序，上下篇与顺序链跳过它们（顺序链变成 15 门，序章/尾声单独成块）；② 保留现序，但在顺序链与上下篇上给横向课加「序章/尾声」视觉标记（复用 `.chip` + `isHorizontal` 字段，learn.astro 已有该字段可用）。倾向 ①——与「线性主线 = 15 知识域课」的口径更自洽。

### C3【低】拓扑序本身无违规（核验通过）

逐条核对 `prereqs` 均满足「前置 order < 本课 order」：multi-agent（system-design #4 / harness #2 < #9）、durable-execution（evaluation #8 < #10）、observability（api #11 < #12）、model-basics（llm-timeline #1 < #15）、framework-ecosystem（agent-harness #3 < #16）、long-term-memory（rag #4 < #13）、data-flywheel（evaluation #8 < #14）。依赖图与 `/learn/` 声称的「拓扑序已校验」相符。

### C4【低】增量主线 M1–M4 判据缺位，课程完成度与主线完成度之间没有中间判据

capstone 设计本身好（每张卡带必修课/参考样本/过关命令，M0 有 `assert:m0` 机器判据），但 M1–M4 状态「练习就位内容留待 sprint 5」——学习者跟到 P1 之后，主线没有可执行的「我到现在该做出什么」判据，只能回课程页看 demo。**建议**：在 capstone.ts 给 M1–M4 各补一条最小机器判据（哪怕只是「复现某 demo 的某条断言输出」），与每课 practicalOutput 里已写明的 `判定 clone 能跑 = …` 命令对齐即可，成本低。

### C5【信息·亮点】渐进披露的地基是好的
