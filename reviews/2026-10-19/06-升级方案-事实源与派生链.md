## 〇、一句话结论

**把「机器可读真源」从 markdown 正文里搬到 `facts/*.json`（写在生成器旁、只由 `npm run facts` 写、被站点/门禁/数据层共用），markdown 与 TS 里的一切数字降级为「派生物」并由 byte 级比对守门——这一步同时消解三类失效：自指不动点（真源移出被测语料即破）、排版欺骗解析器（机器侧改读 JSON，零正则）、手抄副本（TS 侧 5 处改为 import 派生）；而现有 59 条口径门禁全绿的同时 `notes/long-term-memory.md:219/:466` 仍写着已作废的 recall@5=0.44——这就是「必须换成派生、而不是再补一条正则」的活证据。**

## 一、三类失效的机理与实证

### 1.1 隐式耦合：内容编辑静默改变 demo 实测值

耦合的物理路径（全部有据）：

| 环节 | 证据 |
|---|---|
| 语料成员清单硬编码在 demo 里 | `rag-demo/src/corpus.ts:16-20`：`DOCS = [notes/rag.md, notes/agent-harness.md, handoff.md]` |
| 三份文件既是教学内容又是被测输入 | 同上；`rag-demo/src/corpus.ts:1-4` 自述「语料——元选择：课程笔记自己当语料」 |
| 声明值住在其中一份文件里 | `notes/rag.md:283`（chunks）、`notes/rag.md:293`（recall 三值组 + PASS + 日期） |
| 站点构建期解析该声明并直接显示 | `site/src/utils/ragStats.ts:45-83`；消费方 `site/src/pages/index.astro:31,165`、`site/src/pages/works.astro:16,171,186,188-190,193` |
| 本轮实测后果 | `notes/rag.md:293` 三度复跑对照：agent-harness.md 加 §3.4 后 chunk 125→134、@5 0.44→0.38、@10 0.50→0.56 |

**关键判断（与任务描述的一处修正）**：耦合并非「无管理」。`rag-demo/src/check-corpus.ts` 已经会**真跑一遍评测**并与 §13 声明逐项比对（`:156-213`），CI 也确实跑了（`.github/workflows/verify.yml:104-108`）。所以本轮 CI 红**是门禁在正常工作**，不是门禁缺失。

真正未被管理的是另外两件事，见 1.4 与 1.5——那才是本方案的主要靶点。

### 1.2 自指不动点：声明值与实跑值互为因果

`notes/rag.md` 既是语料成员（`rag-demo/src/corpus.ts:17`）又是声明处（`notes/rag.md:283`）。本机实测定界了这条因果链的**可达边界**：

```
承载声明行的 chunk        = rag.md#25
该 chunk 正文长度         = 361 字符（MAX_CHARS=500，chunker.ts:16）
该段可追加余量           = 139 字符
首次分裂阈值             = 追加 ≥434 字 → chunk 总数 134 → 135
```

（实测方法与原始输出见附录 A.3。）

含义：**「改声明」与「改实测值」之间存在一条 139 字符宽的隐形因果通道**。写一句稍长的口径说明就会把声明里的数变成假的。本次迭代到 134 是运气（说明文字短），不是机制保证。

### 1.3 markdown 格式欺骗解析器：排版细节让真源读取静默错位

现行机器读取用的正则（在仓内共 4 份拷贝，见 2.1 A 组）：

```js
/语料[^\n]*?→\s*(\d+)\s*chunks/     // chunks：ragStats.ts:71、check-corpus.ts:39 两份
/recall@3\s*=\s*([0-9.]+)\s*\/\s*recall@5\s*=\s*([0-9.]+)\s*\/\s*recall@10\s*=\s*([0-9.]+)/
                                    // recall 三值组：ragStats.ts:50、check-corpus.ts:152、check-counters.mjs:506 三份
/^##\s*13\b[^\n]*$/m                // §13 小节定位：ragStats.ts:34、check-corpus.ts:144、check-counters.mjs:500 三份
```

本机对同一句声明只改 markdown 排版，实测 8 个变体：

| 排版变体 | 解析结果 |
|---|---|
| 基线（现行） | 134 ✅ |
| `→ **134 chunks**`（粗体） | **125** ❌ 穿透到历史叙述行 |
| `` → `134` chunks ``（行内 code） | **125** ❌ |
| `→ ⇒ 134 chunks`（全角箭头） | **125** ❌ |
| `→ *134* chunks`（斜体） | **125** ❌ |
| `**语料 = … → 134 chunks**`（整行粗体） | 134 ✅ |
| `→` 后换行再写数字 | 134 ✅ |
| 全角逗号 | 134 ✅ |

**8 个变体里 4 个静默读到旧值 125，且不报错。**（实测输出见附录 A.2。）

这就是任务描述的第 3 条失效，已实证。注意它是**双向**危险：既能读到旧值（本例），也能在新旧值同段时随机命中——取决于正则的懒惰匹配与段落里历史叙述的先后顺序。

### 1.4 【本方案头号靶点】绿门禁下的活漂移：recall 副本几乎没有门禁

本机实跑两个门禁，均 exit 0：

```
node site/tools/check-counters.mjs   → ✅ 口径全部一致（判据 59 条 + 副本 7 处）
cd rag-demo && npm run check:corpus  → ✅ 真源 + 8 处副本全部 = 实际 = 134 chunks
                                       ✅ recall 三值组 / PASS / 锚点命中全部 = 实跑（0.31/0.38/0.56）
```

但同一棵树上：

| 位置 | 内容 | 状态 |
|---|---|---|
| `notes/rag.md:293` | recall@3=0.31 / @5=**0.38** / @10=**0.56** | 现值（真源） |
| `notes/knowledge-map.md:19` | 0.31 / 0.38 / 0.56 | ✅ 同步 |
| `README.md:14` | 0.31 / 0.38 / 0.56 | ✅ 同步 |
| `rag-demo/README.md:62-64` | 0.31 / 0.38 / 0.56 | ✅ 同步 |
| `notes/long-term-memory.md:219` | 0.31 / **0.44** / **0.50** | ❌ **陈旧（现值 0.38/0.56）** |
| `notes/long-term-memory.md:466` | 0.31 / **0.44** / **0.50** | ❌ **陈旧** |

**为什么全绿**：`check-corpus.ts` 的副本扫描只扫 `<N> chunks`（`rag-demo/src/check-corpus.ts:77` `CHUNK_NUM = /(\d+)\s*chunks/gi`），**不扫 recall**；recall 只被「§13 声明 vs 实跑」比对（`:175-188`），**不与任何副本比对**。`check-counters.mjs` 的 D6 只查 README 与 rag.md 两处的 recall@5（`:511-512`）。

即：**chunks 的 8 处副本被 `check-corpus.ts` 全扫描，recall 三值组的 14 处落点里只有 2 处被查**（`README.md:14` 与 `notes/rag.md:293`，均只查 @5）。这是「补正则」这个修法的结构性缺陷——每加一条判据都要人手决定查哪个文件的哪个字段，永远追不上副本增长。

`notes/long-term-memory.md:219` 的 0.44 还披着日期外衣（「2026-10-12 锚点式 golden set 复测」），以现在时陈述「系统平均 recall@5 = 0.44」——**读者今天读到的就是错值**。这类「带日期外衣的陈旧副本」比裸错值更难被发现，也正是 `check-counters.mjs:545` `HIST_ALLOW` 豁免规则的盲区（该行含日期，任何行级旧值扫描都会豁免它）。

| 路径 | 跑什么 | 校验 corpus 数字？ |

## 三、真源形态设计（问题 1）

### 3.1 形态：`facts/` 目录 + 每主题一个 JSON

```
facts/
  rag.json          ← rag-demo 主题（chunks / recall / PASS / anchors / date / corpusMembers）
  registry.json     ← 主题清单：生成器命令、prose 副本登记、schema 版本
```

**为什么不是单个 `facts.json`**：不同主题的 schema 不同、Owner（生成器）不同、写入频率不同。单文件会把 9 个 demo 的写入争用与合并冲突压到一个文件上，且任何主题的 schema 升级都会波及其他主题。**粒度取「主题」而非「demo 目录」**：一个 demo 可能有多个主题，而 rag-demo 的 chunks/recall/PASS/anchors 虽是不同的量，却同源、同一次测量产出，故合并为 `rag.json` 一个文件。

**为什么放仓库根 `facts/`**：
1. 它在 `notes/` 之外 → 不进 Astro content collection（`site/src/content/config.ts:13` `base: '../notes'`），不会变成课程页；
2. 它在 `site/` 之外 → 与 `trajectory.ts:51` 读 `harness-demo/` 同构，是仓内已验证的模式；
3. 它在任何 demo 之外 → 不归属单一 demo，符合「跨 demo 共用」的定位；
4. 它在 `.gitignore` 的白名单之外 → 默认入库（`.gitignore` 未忽略 `facts/`）。

**为什么是 JSON 而不是 TS**：JSON 是唯一「人和机器都不会误改结构」的格式——TS 数据文件会被 import、被格式化工具重排、被 tree-shake；JSON 只有一种解析方式（`JSON.parse`），解析失败是响亮失败。

### 3.2 `facts/rag.json` schema（严格，含版本与未知字段拒绝）

```json
{
  "$schema": "./registry.json#/subjects/rag",
  "subject": "rag",
  "schemaVersion": 1,
  "measuredAt": "2026-10-19",
  "corpus": {
    "members": ["notes/rag.md", "notes/agent-harness.md", "handoff.md"],
    "chunks": 134
  },
  "goldenSet": {
    "questions": 10,
    "inScope": 8,
    "outOfScope": 2,
    "recall": { "3": 0.31, "5": 0.38, "10": 0.56 },
    "pass": "3/8",
    "anchorsResolved": "16/16"
  },
  "generator": {
    "command": "npm --prefix rag-demo run facts",
    "entry": "rag-demo/src/facts.ts",
    "nodeVersion": "v22.23.2"
  }
}
```

设计要点：
- **`corpus.members` 必须由生成器从 `rag-demo/src/corpus.ts:16-20` 的 `DOCS` 读出并写入**，不允许在 facts 里手写——这样「语料成员变更」会直接体现在 facts diff 里，隐式耦合第一次变得可见。
- `measuredAt` 每次 `npm run facts` 都更新（诚实记录「上次实测时间」）。代价是每次运行都会脏一个文件——这是**特性不是缺陷**：它让「数字是很久以前测的」无法隐藏。
- 未知字段 / 缺字段 → 加载器 throw（fail-closed）。

### 3.3 谁写谁读

| 角色 | 命令 / 文件 | 依赖 | 写不写文件 |
|---|---|---|---|
| **写方（唯一）** | `npm run facts`（根）→ `node tools/facts.mjs` → 按 `registry.json` spawn 各 demo 的 `npm run facts` → `rag-demo/src/facts.ts` | tsx（在 demo 内） | 写 `facts/*.json`；`--sync` 时才写 TS 数据文件 |
| **便宜门禁** | `npm run facts:check`（根）→ `node tools/facts-check.mjs`，纯 Node 零依赖 | 无 | 不写 |
| **强门禁（测量）** | `npm --prefix rag-demo run check:corpus`（改造后） | tsx | 不写 |
| 读方 · 站点 | `site/src/utils/ragStats.ts`（改造成 JSON loader） | 无 | 不写 |
| 读方 · 门禁 | `site/tools/check-counters.mjs` D6、`rag-demo/src/check-corpus.ts` | 部分需 tsx | 不写 |
| 读方 · 数据层 | `site/src/data/rag-facts.ts`（新）→ 被 `course-structure.ts` / `mvps.ts` / `courses.ts` import | 无 | 不写 |

**根目录为什么也要有 `tools/facts.mjs`**：根 `package.json` 只依赖 `playwright-core`（无 tsx），不能直接跑 `.ts`。故根脚本用纯 Node 做编排，把 `.ts` 抽取器交给各 demo 自己的 tsx 跑——与 `check-corpus.ts:159-161` 用 `process.execPath + process.execArgv` 复用 tsx loader 是同一手法。

### 3.4 `facts:check` 与 `facts` 的分离（fail-open 的关键防线）

`facts:check` **必须零依赖**，否则「生成器跑不起来 → 门禁失效」就会变成 fail-open。零依赖带来三个好处：
1. 能进 `site/build.sh`（本地每次构建都查，与现有两道门禁同格）；
2. 能进 `deploy.yml`（发布路径自查，补 1.5 的洞）；
3. CI 上不需要为它 `npm ci`，不会因装不上依赖而整步跳过。

## 四、自指不动点消解（问题 3）

### 4.1 三个方向评估

**方向 A：把声明行从语料内容里摘出去（§13 不再写数字，只写指针）**

| 维度 | 评估 |
|---|---|
| 破自指 | ✅ 彻底——语料里没有数字，改声明不可能改变测量 |
| 破排版欺骗 | ✅ 彻底（无声明可骗） |
| 教学代价 | ❌ **不可接受**。§13 是「实操复盘」，数字本身就是教学内容（`notes/rag.md:293` 的三度复跑对照是一整段教学设计）。删掉数字等于删课 |
| 结论 | **否决**。违反「不得为迁就架构而削弱内容」 |

**方向 B：声明由生成器写入，gate 守「写入后 = 实跑值」**

| 维度 | 评估 |
|---|---|
| 破自指 | ✅ 有效。不动点从「隐式、靠运气」变成「显式、有界迭代 + 响亮失败」 |
| 破排版欺骗 | ✅ 有效。byte 级比对，任何排版改动即失配 |
| 代价 | 生成器要拥有一段 §13 的渲染模板；§13 变成「部分机器所属」文本 |
| 风险 | ① 模板变更 → §13 大面积重写（需 review）；② 渲染文本变长跨过 chunk 边界 → 不收敛（见 4.3） |
| 结论 | **采用（作为 S1）**，但限定生成区域为一小段、其余 pedagogy 仍手写 |

**方向 C：语料与声明分层（`loadCorpus()` 切掉声明区再切片）**

| 维度 | 评估 |
|---|---|
| 破自指 | ✅ 彻底 |
| 代价 | **语料与「读者看到的笔记」不再一致**。`rag-demo/src/corpus.ts:1-4` 的教学前提「课程笔记自己当语料」会变成假话；且 `notes/rag.md:297` 明写「§13 引述的探针问题原文是稳住排序的关键，严禁改动」，切区可能切到被锚定的文本 |
| 风险 | 高：改变被测对象 = 改变全部 recall 值，且这种改变是「为了架构好看而改测量」，属于放水 |
| 结论 | **否决**。违反「只增约束不放宽」——这是把被测对象改简单了 |

### 4.2 推荐：B 的受限形式（真源外移 + 生成区 byte 守 + 有界迭代）

**第一步（S0，也是收益最大的一步）不碰 rag.md 一个字**，只把机器读取方从「正则解析 §13」切到「`JSON.parse(facts/rag.json)`」。因为 `facts/` 在语料之外，**机器侧的自指当场归零**：站点显示、门禁判据、TS 数据层全部不再依赖 rag.md 的排版。

剩下的自指只存在于「rag.md 的散文数字描述了 rag.md 的测量结果」这一层——这是**人类可读性要求**，不是机器依赖。对它用方向 B：

在 `notes/rag.md` §13 内设一个**定界生成区**（生成器拥有，人禁改）：

```markdown
<!-- facts:generated rag@1 begin -->
> **实测（由 `npm run facts` 生成，勿手改）**：语料 = 课程笔记自己（rag.md + agent-harness.md + handoff.md → 134 chunks）；recall@3 = 0.31 / recall@5 = 0.38 / recall@10 = 0.56（PASS 3/8，2026-10-19 复测；gold 锚点 16/16 全命中）。
<!-- facts:generated rag@1 end -->
```

- 定界符让门禁**无需行号、无需散文正则**就能圈定区域；
- 区域内整段 byte 比对，`**134 chunks**` 这种排版改动立刻失配；
- 区域外的历史叙述（「上一口径 125 chunks」「三度复跑对照」）仍是手写，且**被明确排除在机器读取之外**——这正是现行正则最致命的混淆源；
- 定界符本身进语料，但长度固定 → 是一次性shift，之后稳定（见 4.3）。

### 4.3 有界不动点迭代（写入算法）

`npm run facts` 的写循环：

```
1. measure()                       # loadCorpus() + evaluate，得 actual
2. write facts/<subject>.json      # 真源落盘
3. render §13 生成区               # 由 facts 渲染
4. measure() again                 # 语料已含新生成区
5. if (4) != (1) → 回 2，最多 5 轮
6. 5 轮后仍不等 → exit 1，打印两值，**不写任何文件**
```

第 6 步是必须的：实测声明段有 139 字符余量（1.2），一旦渲染模板变长到跨过 `MAX_CHARS=500`（`rag-demo/src/chunker.ts:16`）就会震荡。**不收敛时必须响亮失败并交给人判断**，而不是悄悄接受一个数。

当前模板长度约 110 字符（作为独立段落），实测追加 434 字才触发分裂（附录 A.3），故现实中有充分余量；迭代守卫是给将来的保险。

## 五、解析健壮性（问题 4）

### 5.1 四候选评估

| 候选 | 抗排版欺骗 | 破自指 | 伤教学可读性 | 本仓机制先例 | 结论 |
|---|---|---|---|---|---|
| **① 独立 facts 文件（JSON）** | ✅✅ `JSON.parse`，markdown 完全不在解析路径上 | ✅ 真源在语料外 | ✅ 零（正文照旧） | `trajectory.ts:51` 构建期跨目录读文件 | **机器侧唯一真源，采用** |
| ② HTML comment 标记 `<!-- fact:chunks=134 -->` | ✅ 锚点是注释语法不是散文形状 | ❌ 注释在语料内 | ✅ 注释不渲染 | 无 | **仅作生成区定界符用**，不当真源 |
| ③ front-matter | ⚠️ 仍是 YAML 文本，且**是原始文件的一部分 → 进语料**（`corpus.ts:25` `readFileSync` 读原文件） | ❌ 自指照旧 | ⚠️ 顶部集中、离 §13 远 | `notes/details/*.md` 有 front-matter（`site/src/content/config.ts:28-36`），但 `notes/*.md` **全无**（本机逐个 `head -1` 确认） | **否决**：既没破自指，又把机器值挪到读者最不看的地方 |
| ④ 散文正则（现状） | ❌ 实测 8 变体 4 个静默读错（1.3） | ❌ | — | `ragStats.ts:50/59/64/71` 等 | **机器侧废除** |

### 5.2 为什么「② 只作定界符、不当真源」

HTML comment 作为真源有两个隐蔽问题：
1. **它仍在语料里**（`corpus.ts:25` 读原始文件全文，注释会被切成 chunk）→ 自指不变；
2. **格式化工具会动它**：Obsidian 保存、prettier、md-log 镜像（`AGENTS.md` 的 `/md-log` 实时镜像进 `notes/*.md`）都可能重排或吞掉注释行。注释不可见 → 被吞了没人发现。

作定界符则没有这两个问题：它的价值是「给门禁一个不依赖行号、不依赖散文形状的圈定边界」，被吞掉本身就会让 `facts:check` 失配 → 响亮失败。

### 5.3 最终解析形态

```
机器读取：facts/rag.json ──JSON.parse──► 站点 / 门禁 / 数据层     （零正则）
人读数字：notes/rag.md §13 生成区 ◄──render(facts)── npm run facts
门禁验证：facts:check 对生成区做 byte 比对 + 对副本登记表逐项比对
```

**一条纪律**：判据的正则必须**由真源值构造**，不得在门禁里写死格式。现行 `check-counters.mjs:510` 已是正例（`new RegExp(...${r5.replace('.','\\.')}...)` 从真源值构造），而 `:568` 的 `/125 chunks/` 是反例（见 6.4）。

### 7.2 明确的 fail-closed 要求（写进实施的硬约束）
