## 0. 硬规则（违反即本次交付失败）

1. **写入边界**：你**唯一**允许写入的文件是本宪章第 5 节分配给你的那一个报告文件。交付前自查 `git status --porcelain`：除 `reviews/` 下新增文件外不得出现任何改动（本仓库起始状态已带若干 ` M` 与 `??`——那是 Lead 接手时的既有状态，**你不得新增**）。
2. **证据自跑**：每条 finding 必须落到 `文件:行号`，并附**你亲自跑过**的命令原文与关键输出；纯阅读类结论写「仅阅读 `path:line`」。**不得**把 `analysis/content/*.md`、`analysis/plan/*.md` 或任何他人报告当证据引用——那些只算**线索**，引用时必须标「线索，未取信」。
3. **未验证就标注**：没跑、跑不通、跑不了的，写「未验证（原因）」。禁止用「应该/显然/一般来说」冒充已核实；禁止把时间先后当因果；机制类结论不能复现就写「未定位」。
4. **不得只看标题下结论**：每条 finding 必须落在具体行上，并**引 ≤2 行原文**。
5. **不用长命令污染本机**：本机 2 vCPU / 3.4GB，swap 已用 1.3G，且同机有对外服务（反向隧道/面板）对内存压力敏感。
   - **禁止**在本机跑 `astro build` / `npm run build`（实测约 484s 且可能 OOM，会把整机拖入换页），**禁止**安装依赖、**禁止**起服务器、**禁止**改仓库。
   - 允许：只读命令（`grep`/`sed`/`find`/`wc`/`node -e` 只读脚本/`curl` 只读拉取线上页面）。单个命令请在 60s 内结束。
6. **外部事实**：需要核实版本号、日期、模型名、外部产品行为时，用 web 检索/抓取**权威一手源**（官方文档、release notes、规范原文），把 URL 写进证据。训练记忆不算证据。
7. **去重与合并**：同一根因只保留一条 finding；命中多处时写在「波及点」里，不要拆成多条刷数量。

## 2. 阅读预算与抽样纪律

每人的阅读预算约 **150–250 KB**，禁止「先把整个语料读完再动手」。做法：

1. **全读**你分区内的 2–4 篇核心文件（逐行）；
2. 其余用 grep 定向抽样（例如按 claim 关键词 `实测|证明|一定|必然|首次|唯一|必须|所有|>=|%` 扫）；
3. **在报告头部的「覆盖声明」里逐字写清**：全读哪些、抽样了哪些节/行、没读什么及原因。
   未声明覆盖的发现视为无效。

## 3. 报告格式（统一，便于复核与聚合）

文件头：

```
# <视角名> 评审报告（<angle>）
- 评审员：<member name>｜时间：2026-10-18 HH:MM（Asia/Shanghai）
- 覆盖声明：
  - 全读（逐行）：<文件清单>
  - 抽样（列节/行）：<...>
  - 未读（原因）：<...>
- 结论摘要：<≤5 条，每条一句话，含最严重项>
- 本轮未验证的范围：<显式列出>
```

每条 finding 用固定字段（markdown 小节，字段必须齐）：

```
### <ANGLE>-F<n>｜<一句话现象>（<严重度>）
- 严重度：blocker | high | medium | low
- 对象：`path:line`（多行给区间）+ ≤2 行原文引文
- 现象：一句话说清错在哪
- 证据：命令原文 + 关键输出（或「仅阅读 path:line」）；外部事实附 URL
- 影响：从**本视角**为什么算问题（读者/考生/接手者会因此误判什么）
- 建议方向：只写方向，不实施（一句话）
- 置信度：高/中/低 + 理由
```

报告末尾附两节：

- `## 正面确认`：在本视角下你**主动查证过且未发现问题**的范围（防确认偏误，必须写，至少 3 条）。
- `## 转交他人`：不属于本视角、但值得他人查的线索（一句话一条，注明建议交给哪个视角）。

**严重度定义**（自设边界＝最危险的失实形态，故逐条对齐）：
- `blocker`：会让读者/考生据此做出**错误行动**（学错顺序、用错 API、误判完成度），或对外声明与事实相反。
- `high`：同一事实存在 ≥2 处互相矛盾的对外表述，或关键事实无法复现/无来源。
- `medium`：表述不准确、过时、误导性措辞，但不直接导致错误行动。
- `low`：文风、排版、措辞、可读性瑕疵。
